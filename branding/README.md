# branding/

Master source files for ConcatCNC's visual identity live here — nowhere else. Everywhere else in the repo (`app/img/`, `app/icon.png`, `app/icon.ico`, `build/icon.*`, `app/jog/*.png`, `app/favicon.ico`, etc.) holds a *derived* copy exported from these masters at a specific size/format for a specific consumer. When the branding changes, it changes here first, then gets re-exported outward — never edit a derived copy directly and expect it to stick.

Four master SVGs live here (replaced 2026-09-07 — the prior single-logo set is in `File13/branding/`):

- `logo-master-light.svg` — full logo (wordmark + cat mark), for placement on light backgrounds (black outline on the wordmark). Source for `app/img/concatcnc-logo-light.svg`, shown on the splash screen and title bar whenever the app is in light mode.
- `logo-master-dark.svg` — same logo, redrawn for dark backgrounds (white-ish outline so it stays legible on dark surfaces). Source for `app/img/concatcnc-logo-dark.svg`, shown in the same two spots whenever the app is in dark mode. The swap between the two is automatic — see `Theme.set()`/`ThemeData.init()` in `app/js/theme.js`, which sets `#logosplashimg`/`#windowtitlebarlogo`'s `src` based on the current theme. (If light/dark ever look swapped again: it's the *outline color* inside each file that must match its filename, not the JS mapping — check `stroke:` on the text paths before touching `theme.js`.)
- `icon-master.svg` — the full square icon/mark (cat + cage bars), no wordmark. Used at every size ≥64px: the desktop app icon (`app/icon.png`, `build/icon.png`, `build/icons/{64,96,128,256,512}.png`), the larger entries in `app/icon.ico`/`build/icon.ico`/`build/icon.icns`, the Mobile Jog PWA's larger icons (`app/jog/apple-touch-icon.png` 180px, `app/jog/android-chrome-*.png`), and the in-app ribbon "Visit" button icon (`app/img/concatcnc-icon.svg` — confirmed via a rendered light-vs-dark-background comparison that its red outline reads fine either way, so it doesn't need a light/dark split like the logo does).
- `icon-master-small.svg` — the same mark with the cage-bars group removed, cat silhouette only. The full icon's cage bars + thin outline don't survive being shrunk to real taskbar/favicon sizes (measured: at 32px the artwork is a muddy blob no matter how well it's rasterized — this isn't a rasterization bug, the linework is just too fine for that pixel budget). Used for every size <64px: `build/icons/{16,24,32}.png`, `app/favicon.ico` and `app/jog/favicon.ico` (16/32/48, all simplified — favicons are always shown tiny), `app/jog/favicon-{16,32}.png`, and the small entries inside `app/icon.ico`/`build/icon.ico` (16/24/32/48) and `build/icon.icns` (the 32px `ic11` entry, i.e. 16pt@2x).

**`app/icon.ico` vs `app/icon.png`:** `index.js`'s `iconPath` (used for the `BrowserWindow` icon, tray icon, and overlay icon) points at `app/icon.ico` on Windows specifically, not `app/icon.png` — `nativeImage.createFromPath` on an `.ico` exposes every size embedded in it to Windows, which then picks the best match per context (taskbar button, title bar, alt-tab, tray), so the taskbar gets the simplified small icon instead of the full detailed one crushed down to 16-32px. Other platforms fall back to the plain `app/icon.png` (single image, full detail) since they don't get that same multi-resolution behavior from an `.ico`.

When any of these four change again: replace the file(s) here, then re-export every derived copy listed above at its existing size/format, using `icon-master-small.svg` for anything under 64px and `icon-master.svg` at 64px and up (rasterize each SVG at each target pixel size — a plain browser screenshot works fine for this **as long as the `<img>` is forced to `width:100%;height:100%;object-fit:contain` in the render harness, not `max-width/max-height:100%`**, which only caps growth and will silently render the artwork tiny within a mostly-transparent canvas at any target size larger than the SVG's own declared `width`/`height` attributes — this bit precisely 2026-09-07 and produced a `build/icon.png`/`build/icons/512.png`/etc. that wasted most of their resolution on transparent padding; verify by checking the rendered PNG's actual ink bounding box isn't tiny relative to the canvas before trusting a "looks fine" glance, since a transparent-background PNG previews as plain white in most simple viewers regardless of whether it's actually correct). Repack `build/icon.ico`/`app/icon.ico`/`build/icon.icns` as PNG-embedded ICO/ICNS containers — see the git history around 2026-09-07 for the exact scripts used, no external image tools (ImageMagick/Inkscape/sharp/etc.) were needed or would have prevented either mistake above.
